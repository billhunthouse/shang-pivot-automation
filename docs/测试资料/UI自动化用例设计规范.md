# UI 自动化测试用例设计规范

> 版本：1.0  
> 日期：2026-11-15  
> 适用项目：尚品汇电商系统（管理端 + 商城 C 端）  
> 技术栈：Playwright (Python) + pytest + Allure 3

## 1. 目的

这份规范解决三个问题：

1. 从需求文档中**稳定地提取 UI 测试点**，而不是凭经验点页面；
2. 让 UI 自动化用例**可读、可维护、可定位**；
3. 让每一次执行都有**步骤级截图和可追溯证据**，报告能直接用于评审和缺陷复现。

## 2. 适用范围

适用于：

- 管理端（Element Plus，`shang-admin-web`）；
- 商城 C 端 Web/H5（Vant，`shang-mall`）；
- 跨端、跨角色的业务流程（顾客下单 → 管理员发货 → 顾客收货/评价）；
- 页面级表单校验、权限守卫、状态展示、空态/异常态。

不适用于：

| 类型 | 更适合的方式 |
|---|---|
| 接口字段、错误码、并发、幂等 | API 自动化 |
| 像素级视觉差异 | 视觉回归（截图对比） |
| 大压力/长稳压测 | k6 / JMeter |
| 安全渗透、越权扫描 | 安全专项 |
| 纯算法/工具函数 | 单元测试 |

> 原则：UI 自动化只验证“用户能感知的行为”，不重复 API 已经覆盖的底层契约。

## 3. 从需求文档提取 UI 测试点

### 3.1 输入材料

| 材料 | 提取内容 |
|---|---|
| PRD | 角色、入口、字段规则、状态、异常提示、验收标准 |
| 原型/截图 | 页面结构、按钮位置、弹窗层级、空态 |
| 接口文档 | 页面动作对应的真实请求、错误码 |
| 数据字典 | 状态枚举、边界值、必填/可空 |
| 现有代码 | 实际选择器、条件渲染、权限判断 |

### 3.2 提取步骤

```text
Step 1 找角色：谁在什么入口做什么
Step 2 找页面：路由、页面状态、弹窗/抽屉
Step 3 找动作：点击、输入、选择、提交、取消
Step 4 找规则：必填、长度、格式、状态前置条件
Step 5 找反馈：成功提示、错误提示、列表刷新、跨端可见
Step 6 找异常：空态、无权限、重复操作、网络失败
Step 7 找数据：操作后 UI 与接口/数据库是否一致
```

### 3.3 需求条目到测试点的映射模板

| 需求条目 | UI 测试点 | 优先级 |
|---|---|---|
| 入口存在 | 菜单/按钮可见、可点击、路由正确 | P0 |
| 字段规则 | 必填、长度、格式、边界、错误提示位置 | P1 |
| 状态前置 | 非允许状态按钮禁用/提示 | P1 |
| 成功反馈 | toast/弹窗关闭/列表刷新 | P1 |
| 跨端展示 | C 端页面同步可见 | P0 |
| 权限 | 未登录/低权限被拦截 | P1 |
| 数据一致性 | UI 展示 = 接口返回 = 数据库 | P1 |
| 异常/空态 | 空列表、加载失败、超时 | P2 |
| 安全 | XSS 内容按文本渲染、敏感信息脱敏 | P2 |

## 4. 验证点维度清单

每一条 UI 用例至少覆盖一个维度，核心链路至少覆盖 6 个。

### 4.1 页面与路由

- 路由是否可达，URL 是否正确；
- 刷新、直接输入 URL、前进/后退是否正常；
- 未登录/无权限是否跳登录或提示；
- 页面标题、面包屑、菜单高亮是否正确。

### 4.2 元素与文案

- 关键元素存在且可见；
- 按钮文案、字段标签、单位、占位符正确；
- 禁用态、加载态、空态、错误态；
- 图标/图片加载失败是否有兜底。

### 4.3 交互状态

- 默认、悬停、聚焦、点击、禁用；
- 弹窗打开/关闭、遮罩点击、ESC；
- 表格排序、筛选、分页；
- 表单联动（选择规格后价格/库存变化）。

### 4.4 表单校验

- 必填、空白、纯空格；
- 长度边界（最小/最大/超长）；
- 格式（手机号、邮箱、金额、日期）；
- 错误提示**位置**（内联 vs toast）；
- 错误提示在修正后是否消失；
- 提交按钮是否防重复点击。

### 4.5 业务流程与状态

- 正常主流程；
- 状态前置条件（仅待发货可发货）；
- 状态迁移后的页面展示；
- 重复操作（重复提交、重复回复）；
- 取消/返回是否回滚。

### 4.6 数据一致性

- 列表展示与详情一致；
- 操作后列表/详情/统计同步刷新；
- UI 展示与接口返回一致；
- 关键字段（金额、库存、状态、ID）不丢失精度。

### 4.7 跨端与跨角色

- 管理端操作后 C 端可见；
- C 端提交后管理端可查；
- 顾客 A 不能看到顾客 B 的数据；
- 管理端与 C 端 token 不混用。

### 4.8 异常与空态

- 无数据、全部隐藏、搜索无结果；
- 接口 4xx/5xx 的页面提示；
- 网络超时、重复提交；
- 图片/附件上传失败。

### 4.9 安全

- 用户输入按文本渲染，不执行 HTML/JS；
- 手机号、地址、支付信息脱敏；
- 未登录不能直接访问受保护路由；
- 越权 URL 不能打开他人订单/售后。

### 4.10 可访问性与兼容性

- 关键按钮有可读名称（`aria-label`/文本）；
- 键盘 Tab 可达；
- 1440×900、1280×800、390×844 三档视口；
- Chromium 基线，必要时补 WebKit。

## 5. 用例分层

| 层级 | 目的 | 数量建议 | 示例 |
|---|---|---|---|
| L0 冒烟 | 页面能打开、核心元素存在 | 每模块 1-2 条 | 管理端登录、商城首页 |
| L1 核心链路 | 一条完整用户旅程 | 每版本 2-4 条 | 下单→支付→发货→收货 |
| L2 功能 | 单功能正常/异常 | 每功能 3-8 条 | 回复评价、隐藏评价 |
| L3 边界/权限 | 边界、异常、越权 | 按风险 | 空回复、501 字、未登录 |
| L4 视觉/可访问性 | 布局、文案、对比度 | 抽样 | 关键页面截图基线 |

## 6. 用例结构与命名

### 6.1 ID 规范

```text
UI-<模块>-<序号>
UI-REPLY-001
UI-CORE-001
UI-AUTH-001
```

### 6.2 标题规范

```text
<动作> + <对象> + <预期结果>
例：管理员回复评价后，C 端商品详情展示商家回复
```

### 6.3 一条用例只验证一个主行为

反例：

```text
登录 → 加购 → 下单 → 支付 → 发货 → 评价（全部断言混在一条）
```

正例：

```text
UI-CORE-001 顾客完成下单支付
UI-CORE-002 管理员对待发货订单发货
UI-CORE-003 顾客确认收货后可评价
```

> 长链路可以拆成多条，用共享 fixture 传递订单号；不要把所有断言塞进一条。

### 6.4 步骤模板

```text
Given 前置条件（登录态、数据、状态）
When  用户动作（点击/输入/提交）
Then  可观察结果（页面/接口/数据库）
And   截图证据
```

## 7. 选择器规范

优先级从高到低：

1. `get_by_role` + 可读名称；
2. `get_by_label` / `get_by_placeholder`；
3. `data-testid`；
4. 稳定的业务文本；
5. CSS 类（仅限语义类）；
6. 禁止 `nth-child`、绝对 XPath、依赖 DOM 顺序。

示例：

```python
page.get_by_role("button", name="保存回复").click()
page.get_by_placeholder("请录入运单号").fill("SF123456")
page.locator("tr", has_text="O202611122012190001")
```

建议给关键元素补 `data-testid`：

```html
<button data-testid="review-reply-save">保存回复</button>
```

## 8. 等待与稳定性

- 优先使用 Playwright 自动等待和 `expect(...).to_be_visible()`；
- 禁止 `sleep(3)` 这类固定等待；
- 等待**业务信号**：URL 变化、弹窗关闭、toast 出现、列表行出现；
- 对异步刷新使用 `expect(locator).to_have_text(...)` 轮询；
- 每个测试独立 context，避免 cookie/localStorage 污染；
- 失败时保存截图、URL、console、network 摘要。

## 9. 测试数据管理

| 原则 | 做法 |
|---|---|
| 可重复 | 使用固定测试账号/固定评价，测试后恢复 |
| 隔离 | 每个用例生成唯一业务标识（时间戳/随机串） |
| 最小 | 只造当前用例需要的数据 |
| 可清理 | fixture teardown 恢复原值；无法清理时记录 |
| 不依赖顺序 | 用例可单独运行、可乱序运行 |
| 不污染生产 | 只连本地/测试环境 |

本项目的做法：

- 管理员：`admin / Admin@123`（本地）；
- 顾客：`13800000001 / 验证码 123456`；
- 评价回复用例固定评价 `8503`，fixture 记录并恢复原回复；
- 无回复评价 `8501`、隐藏评价 `8504` 用作对照；
- 订单号、回复内容带时间戳，避免重复。

## 10. 截图与证据规范

### 10.1 每一步都要截图

```python
from contextlib import contextmanager
import allure

@contextmanager
def step(page, title):
    with allure.step(title):
        yield
        allure.attach(
            page.screenshot(full_page=True),
            name=f"{title}.png",
            attachment_type=allure.attachment_type.PNG,
        )
```

要求：

- 每个 `allure.step` 结束后自动截图；
- 截图命名 = 步骤名，便于报告阅读；
- 关键操作前后各一张（如保存前/保存后）；
- 失败时额外保存当前 URL、console、失败截图；
- 截图使用 `full_page=True`，避免只看到半屏。

### 10.2 证据链

```text
用例标题
  └── step 1 打开页面 [截图]
  └── step 2 填写表单 [截图]
  └── step 3 提交 [截图]
  └── step 4 列表回查 [截图]
  └── step 5 C 端验证 [截图]
```

报告中任何人点开用例，都能按步骤还原现场。

## 13. 反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 一条用例几十步 | 失败难定位 | 拆分，共享 fixture |
| `sleep` 等待 | 慢且不稳定 | 等业务信号 |
| CSS 绝对路径 | 改样式就挂 | role/testid |
| 依赖执行顺序 | 单独跑失败 | 每条独立 |
| 只断言 toast | 数据可能没落库 | 列表/接口/DB 回查 |
| 不截图 | 报告无法复现 | 每步截图 |
| 用生产数据 | 污染/泄露 | 专用测试数据 |
| 断言全部字段 | 维护成本高 | 断关键字段 + 契约 |

## 15. 覆盖率计算

UI 覆盖率不是单一百分比，推荐同时看：

| 指标 | 公式 | 说明 |
|---|---|---|
| 页面覆盖率 | 被通过用例访问并断言的页面数 ÷ 总页面数 | 只证明“页面可达+关键内容渲染” |
| 需求触达率 | 至少一个页面被覆盖的需求数 ÷ 总需求数 | 证明需求有 UI 落点 |
| 需求行为覆盖率 | Σ(需求权重) ÷ 总需求数；full=1、partial=0.5 | 证明具体行为有断言 |
| 用例通过率 | 通过用例数 ÷ 执行用例数 | 执行质量 |
| 步骤证据覆盖率 | 附件数 ≥ 步骤数的通过用例数 ÷ 通过用例数 | 证明每一步有截图 |
| 角色覆盖率 | 已执行角色数 ÷ 定义角色数 | guest/customer/admin |
| 视口覆盖率 | 已执行视口档位数 ÷ 定义档位数 | 桌面 + H5 |
| 浏览器覆盖率 | 已执行浏览器数 ÷ 目标浏览器数 | Chromium/WebKit/Firefox |

生成方式：

```bash
cd api_testcases
python3 scripts/ui_coverage.py   --results artifacts/allure-ui-results   --out-md ../docs/测试资料/UI覆盖率报告.md   --out-json artifacts/ui-coverage.json
```
