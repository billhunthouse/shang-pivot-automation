# 评价商家回复 — 复盘与深化建议

> 日期：2026-11-12  
> 范围：需求 → LLM-wiki 影响分析 → 开发 → API/UI 自动化 → Allure  
> 结果：8 条测试全部通过（API 7 + UI 1），Allure 100%

## 1. 做得好的地方

1. **先查 wiki 再改代码**：`data/pages.json` + `data/apis.json` 快速确认评价管理页和商品详情页的调用面，避免只改后端漏掉 C 端展示。
2. **改动边界小**：只动 `commerce.review` 两列和评价相关 Controller/Service/UI，不触碰订单、库存、支付、售后主链路。
3. **API + UI 双闭环**：API 验证契约和 C 端数据可见性，UI 验证“管理员点击回复 → 商城详情展示”的真实用户路径。
4. **Allure 统一报告**：API 与 UI 用例进入同一份报告，便于按 feature/story 查看。
5. **负面/边界覆盖**：未登录、空、超长、404、重复回复、隐藏评价。
6. **文档闭环**：PRD、影响分析、测试用例、执行记录、复盘均在仓库内。

## 2. 可以精炼的地方

### 2.1 测试数据隔离（优先级最高）

当前 API/UI 用例复用了种子评价 `8503`，回复会真实落到本地库，重复执行会覆盖上一条回复。

改进：

- 增加专用测试评价 fixture：通过已完成订单创建一条专属评价，或准备 SQL seed；
- 测试结束用专用清理 API/DB 事务还原；
- UI 用例按专用评价 ID 定位，不依赖「打工人神器」文案。

### 2.2 选择器稳定性

管理端 UI 无 `data-testid`，当前用「打工人神器」文本定位；文案变化会导致用例失效。

改进：

- 给评价行、回复按钮、回复弹窗增加 `data-testid`；
- 表格行使用评价 ID 定位（如 `data-review-id`）。

### 2.3 Allure 环境信息

报告能展示 8 条用例，但 Environment 区域为空。

改进：

- 在 `api_testcases/conftest.py` 补充 `environment.xml` 或确认 Allure 2.16 的 environment 文件格式；
- 写入 BASE_URL、ADMIN_BASE_URL、MALL_BASE_URL、RUN_ID、UI/API 标记。

### 2.4 覆盖深化

| 方向 | 建议用例 |
|---|---|
| 边界 | 500 字通过、501 拒绝、纯空白、换行、emoji |
| 安全 | `<script>`/`<img onerror>` 内容，前端必须按文本渲染 |
| 权限 | 低权限管理员/无 token/过期 token |
| 审计 | 操作日志含 review id、reply action、操作人 |
| 并发 | 两管理员同时回复、回复与隐藏并发 |
| 一致性 | 回复后评价 rating/status/content 不变 |
| 历史 | 是否需要回复历史（当前只保留最新一条） |
| 通知 | 回复后是否通知顾客（当前无） |

### 2.5 后端校验深化

- 500 字按 `String.length()` 计，中文/emoji 的“字数”口径需产品确认；
- 回复允许换行，但需要限制连续空行/首尾空白；
- 回复内容是否允许 URL/手机号，需要内容安全策略；
- `updateById` 返回值未检查，极端并发下可能静默失败。

## 3. 可深化的产品能力

1. **回复模板**：物流延迟、质量问题、感谢好评等快捷模板。
2. **回复历史**：保留多次回复/修改记录，支持审计。
3. **回复状态**：待回复/已回复筛选，客服工作台。
4. **顾客通知**：回复后站内信/推送。
5. **评价分析**：低星评价回复率、平均响应时长、商家回复覆盖率。
6. **多语言/多店铺**：如果平台扩展多租户，需要 `merchant_id` 和 locale。
7. **内容安全**：敏感词、联系方式、广告内容过滤。

## 4. 工程化提升

- 把 `review-reply` 用例加入 `pytest` 回归集（P1），而不是一次性脚本；
- CI 中跑 API 全套 + UI smoke，Allure 作为构建产物；
- 用 `data-testid` + 专用 seed 数据降低 UI 脆弱性；
- 把新增端点补进 `api_testcases/scripts/build_api_doc.py` 的生成结果、OpenAPI 和 LLM-wiki；
- 每次功能变更后重跑 `docs/llm-wiki/scripts/build_wiki.py`，保持需求/页面/接口/代码图谱新鲜；
- 若后续做 RBAC，给 `review:reply` 增加权限点与菜单按钮控制。

## 5. 本次经验教训

- **LLM-wiki 很有用，但不能替代源码验证**：页面 import 映射是启发式，评价管理页的实际 API 还要回 `reviews.ts` 确认。
- **UI 测试的最后一步一定要跨端**：只测管理端保存成功，不能证明 C 端展示正确；本次用商品详情页闭环。
- **“保存成功”不等于“数据正确”**：API 用例回查了管理端列表、C 端评价列表、商品详情 `reviewsPreview` 三处。
- **测试数据是最大债务**：下一轮优先做专用评价 fixture 和清理，不然用例会越来越依赖种子数据。
