> 日期：2026-11-15  
> 接口：`POST /api/orders`  
> 环境：本地（后端 8086 / PostgreSQL 55434 / Redis 56379）  
> 压测：k6 v2.3.0  
> 监控：Prometheus 19090 + Grafana 13000  
> 关联报告：
> - `docs/测试资料/下单接口-300并发性能测试报告.md`

## 1. 结论摘要

300 VU 持续 20s 的主场景结果：

| 指标 | 优化前 | P0 优化后（三次中位） | 结论 |
|---|---:|---:|---|
| 总请求 | 7,651 | 7,716 | 基本持平 |
| RPS | 369.2 | 367.3 | 基本持平 |
| 平均延迟 | 294.6ms | 293.6ms | 基本持平 |
| P95 | 794.0ms | 809.6ms | 基本持平 |
| P99 | 1,287.7ms | 1,268.9ms | 基本持平 |
| 失败率 | 0% | 0% | 稳定 |

300 VU 一次性突刺：

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| RPS | 220.0 | 331.3 | +50.6% |
| 平均延迟 | 792.7ms | 448.7ms | -43.4% |
| P95 | 1,105.5ms | 696.0ms | -37.0% |

**核心判断：**

1. P0 解决了连接池和线程池的硬瓶颈，突刺场景改善明显；
2. 持续场景的瓶颈已经从“连接池/线程池”转移到“同一 SKU 的库存行锁”；
3. 继续加大连接池不会继续提升持续吞吐，下一步应做库存热点隔离；
4. 本轮只改了 P0，P1/P2 项保持原状。

## 2. 测试场景说明

```text
executor: constant-vus
vus: 300
duration: 20s
think time: 0.5s
接口: POST /api/orders
账号: 300 个独立会员，每个会员 1 个默认地址
商品: SPU 111 / SKU 10012
库存: 临时调高到 100,000
```

总请求不是 `300 × 20 = 6,000`，因为 300 VU 是**并发用户数**，不是 300 RPS：

```text
单次循环 ≈ 下单响应 0.29s + think time 0.5s ≈ 0.79s
每个 VU 20s ≈ 20 / 0.79 ≈ 25.3 次
300 VU × 25.3 ≈ 7,590 次
实际 7,651 次
```

如果需要精确 6,000 个请求，应使用：

```js
executor: 'shared-iterations'
vus: 300
iterations: 6000
```

或恒定到达速率：

```js
executor: 'constant-arrival-rate'
rate: 300
timeUnit: '1s'
duration: '20s'
```

## 3. 优化问题清单

### 3.1 P0：已修复

| ID | 分类 | 问题 | 证据 | 影响 | 修复 |
|---|---|---|---|---|---|
| PERF-001 | 连接池 | Hikari `maximum-pool-size=5` | 监控 active=5，pending 峰值 195 | 300 请求只有 5 个 DB 事务能执行 | 改为 20，最小空闲 5 |
| PERF-002 | Web 容器 | Tomcat 默认 max threads=200 | busy 峰值 200/200 | 300 VU 中约 100 个在 accept 队列 | max-threads=400，accept-count=300 |
| PERF-003 | 代码/SQL | 每单 3 次系统配置查询 | `OrderSubmitService` 76–80 行 | 每单多 3 次 SQL | Caffeine 缓存 5 分钟 + 更新 evict |
| PERF-004 | 代码/SQL | 每单 2 次会员查询 | `isActive` + `maskedPhone` 各一次 selectById | 每单多 1 次 SQL | 新增 `findActive` 单查询 |
| PERF-005 | 代码/SQL | stock 先 `SELECT FOR UPDATE` 再 `updateById` | `OrderSubmitService.lockStock` | 两次往返、持锁时间长 | `UPDATE ... RETURNING` CTE 原子锁定 |
| PERF-006 | SQL 索引 | `order_item` 无 `order_id` 索引 | EXPLAIN：Seq Scan 8,197 行 7.9ms | 订单详情/关单线性扫描 | V23 增加 `idx_order_item_order_id` |

## 4. P0 修复详情

### 4.1 HikariCP 连接池

```yaml
# backend/shang-server/src/main/resources/application.yaml
hikari:
  maximum-pool-size: ${DB_POOL_MAX:20}
  minimum-idle: ${DB_POOL_MIN_IDLE:5}
```

优化后：

```text
hikaricp_connections_max     = 20
hikaricp_connections_active  = 20
hikaricp_connections_pending = 135~179
```

pending 仍高，但不再被 5 个连接硬卡住；后续受同一 SKU 行锁限制。

### 4.2 Tomcat 线程池

```yaml
server:
  tomcat:
    threads:
      max: ${TOMCAT_MAX_THREADS:400}
      min-spare: ${TOMCAT_MIN_SPARE_THREADS:20}
    accept-count: ${TOMCAT_ACCEPT_COUNT:300}
```

优化后：

```text
tomcat_threads_config_max_threads = 400
tomcat_threads_busy_threads       = 193~284
```

不再出现 200/200 打满。

### 4.3 系统配置缓存

```java
// SystemConfigApiImpl
Cache<String, Optional<String>> cache = Caffeine.newBuilder()
        .maximumSize(200)
        .expireAfterWrite(Duration.ofMinutes(5))
        .build();
```

配置更新接口：

```java
systemConfigApi.evict(cfg.getConfigKey());
```

效果：下单链路 3 次配置查询不再每单打 DB。

### 4.4 会员查询合并

```java
// CustomerQueryApi
ActiveCustomer findActive(Long customerId);

// OrderSubmitService
CustomerQueryApi.ActiveCustomer activeCustomer = customerQueryApi.findActive(customerId);
```

一次 `selectById(customer)` 同时完成状态判断和手机号脱敏，减少 1 次 SQL/单。

### 4.5 stock 原子锁定

```sql
WITH updated AS (
    UPDATE commerce.stock
    SET locked_stock = COALESCE(locked_stock, 0) + #{qty},
        updated_at = NOW()
    WHERE id = (
        SELECT id FROM commerce.stock
        WHERE sku_id = #{skuId} AND deleted = FALSE
        ORDER BY id LIMIT 1
    )
      AND COALESCE(physical_stock, 0) - COALESCE(locked_stock, 0) >= #{qty}
    RETURNING warehouse_id
)
SELECT warehouse_id FROM updated
```

把“检查可售 + 锁定”合并为一条 SQL，返回 null 表示库存不足。

### 4.6 order_item 索引

```sql
-- V23__order_item_order_id_index.sql
CREATE INDEX IF NOT EXISTS idx_order_item_order_id
    ON commerce.order_item (order_id)
    WHERE deleted = false;
```

验证：

```text
优化前：Seq Scan 8,197 行，7.933ms
优化后：Index Scan，0.098ms
```

## 7. 下一轮建议

### 第一优先：库存热点隔离（PERF-007）

同一 SKU 是当前持续场景的最终瓶颈。可选方案：

1. **按仓库拆 stock 行**：同一 SKU 多仓库存，下单按仓分流；
2. **库存令牌/预分配**：Redis 或本地令牌桶预扣，DB 异步落账；
3. **热点 SKU 队列**：单 SKU 请求串行入队，批量落库；
4. **业务限流**：秒杀类 SKU 单独限流，避免打满通用下单池。

> 这部分属于 P1/P0 下一轮，不在本次“只修 P0”范围。

### 第二优先：并发正确性

- 幂等键唯一冲突捕获（PERF-008）；
- 订单号改数据库序列/雪花（PERF-009）；
- 事务收窄（PERF-010）。

### 第三优先：可观测与工程化

- `pg_stat_statements`（PERF-012）；
- Hikari pending / Tomcat busy 告警；
- 压测数据自动清理（PERF-014）；
- CI 性能基线。
