# 下单接口 300 并发性能测试报告

> 日期：2026-11-15  
> 接口：`POST /api/orders`  
> 场景：300 并发下单  
> 环境：本地（8086 / PostgreSQL 55434 / Redis 56379）  
> 压测工具：k6 v2.3.0  
> 监控：Prometheus 19090 + Grafana 13000
> P0 优化复测：[下单接口-300并发P0优化复测报告.md](下单接口-300并发P0优化复测报告.md)  
> 问题汇总：[性能测试优化问题汇总.md](性能测试优化问题汇总.md)

## 1. 结论摘要

| 指标 | 结果 |
|---|---:|
| 并发 VU | 300 |
| 持续时长 | 20s |
| 总请求 | 7,651 |
| 成功率 | 100% |
| 客户端 RPS | 369.2 |
| 平均延迟 | 294.6ms |
| P95 | 794.0ms |
| P99 | 1,287.7ms |
| 最大延迟 | 1,456.1ms |
| Hikari 活跃连接 | 5 / 5 |
| Hikari 等待连接峰值 | 195 |
| Tomcat busy 线程峰值 | 200 / 200 |
| PostgreSQL 锁等待峰值 | 4 |
| 数据库死锁 | 0 |

结论：**300 并发下接口全部成功，但系统已进入明显的排队区间**。主要瓶颈不是 CPU，而是：

1. HikariCP 连接池只有 **5** 个连接，等待队列峰值 **195**；
2. Tomcat 工作线程 200 被打满，300 VU 中有约 100 个在排队；
3. 同一 SKU 的 `SELECT ... FOR UPDATE` 行锁串行化，锁等待峰值 4；
4. 单笔订单约 13 次 SQL，其中 3 次系统配置查询、2 次会员查询可以缓存/合并；
5. `commerce.order_item` 缺少 `order_id` 索引，订单详情/关单查询走 Seq Scan。

## 5. 瓶颈分析

### 5.1 HikariCP 只有 5 个连接（首要瓶颈）

代码/配置证据：

```yaml
# backend/shang-server/src/main/resources/application.yaml
hikari:
  maximum-pool-size: 5
  minimum-idle: 1
```

监控证据：

```text
hikaricp_connections_active  = 5
hikaricp_connections_pending = 195（峰值）
hikaricp_connections_max     = 5
```

含义：

- 300 个请求同时到达时，只有 5 个数据库事务能真正执行；
- 其余 195 个请求在 Hikari 队列等待；
- 等待时间直接进入接口 P95/P99；
- 即使 Tomcat 有 200 个线程，真正能干活的数据库连接只有 5 个。

依据：Grafana Hikari 面板 `01-hikari.png`；Prometheus `max_over_time(hikaricp_connections_pending[30s]) = 195`。

### 5.2 Tomcat 工作线程打满

监控证据：

```text
tomcat_threads_config_max_threads = 200
tomcat_threads_busy_threads       = 200（峰值）
```

含义：

- 300 VU 同时请求，Tomcat 最多 200 个工作线程；
- 另外约 100 个连接在 accept 队列/内核队列等待；
- 线程数打满后，新请求即使拿到线程也要等 Hikari 连接，形成双重排队。

依据：Grafana Tomcat 面板 `02-tomcat.png`。

### 5.3 同一 SKU 的行锁串行化

代码证据：

```java
// OrderSubmitService.lockStock
Stock stock = stockMapper.selectOne(new LambdaQueryWrapper<Stock>()
        .eq(Stock::getSkuId, skuId)
        .last("LIMIT 1 FOR UPDATE"));
...
stock.setLockedStock(locked + qty);
stockMapper.updateById(stock);
stockLogMapper.insert(logRow);
```

监控证据：

```text
pg_activity_lock_wait = 4（峰值）
pg_locks_waiting      = 4（峰值）
```

含义：

- 300 VU 全部抢同一个 SKU 的 stock 行；
- `FOR UPDATE` 让同一 SKU 的下单串行；
- 每个事务持有连接等锁，进一步放大 Hikari 排队；
- 生产环境多 SKU 会分散，但秒杀/爆款仍会复现。

依据：Grafana 数据库会话/锁等待面板 `03-db-sessions.png`。

### 5.4 单笔订单 SQL 次数偏多

按 `OrderSubmitService.submit` 代码路径静态计数：

| 步骤 | SQL |
|---|---:|
| `customerQueryApi.isActive` | 1 |
| 幂等键查订单 | 1 |
| 查地址 | 1 |
| 查 SKU | 1 |
| 查 SPU | 1 |
| `stock ... FOR UPDATE` | 1 |
| 更新 stock | 1 |
| 写 stock_log | 1 |
| `systemConfigApi.getValue` × 3 | 3 |
| `customerQueryApi.maskedPhone` | 1 |
| 插入 order | 1 |
| 插入 order_item | 1 |
| **合计** | **约 13 次 SQL/单** |

其中可优化项：

1. **系统配置 3 次查询**：`freight.free-threshold`、`freight.default-amount`、`order.pay-timeout-minutes` 都是低频变更配置，适合本地缓存（Caffeine，TTL 1~5 分钟），可减少 3 次 SQL/单。
2. **会员信息 2 次查询**：`isActive` 和 `maskedPhone` 都 `selectById(customerId)`，可合并为一次查询或在请求级缓存，减少 1 次 SQL/单。
3. **stock 读改写 3 次 SQL**：可改成一条原子更新：

```sql
UPDATE commerce.stock
SET locked_stock = locked_stock + #{qty}
WHERE sku_id = #{skuId}
  AND deleted = false
  AND physical_stock - locked_stock >= #{qty};
```

检查影响行数为 1 表示锁定成功，0 表示库存不足；再写 `stock_log`。这样减少一次 select + update 的往返，并缩短持锁时间。

### 5.5 order_item 缺少 order_id 索引

`EXPLAIN (ANALYZE, BUFFERS)` 证据（`artifacts/perf-300u/sql-explain.txt`）：

```text
Seq Scan on order_item  (cost=0.00..301.48 rows=1 width=283)
  Filter: ((NOT deleted) AND (order_id = '...'::bigint))
  Rows Removed by Filter: 8197
  Execution Time: 7.933 ms
```

含义：

- `order_item` 当前只有主键索引，没有 `order_id` 索引；
- 订单详情、关单、售后关联订单明细都会扫全表；
- 当前 8,197 行只是 7.9ms，订单量到百万级会线性恶化。

建议：

```sql
CREATE INDEX idx_order_item_order_id
  ON commerce.order_item (order_id)
  WHERE deleted = false;
```

### 5.6 已确认不是瓶颈的点

| 查询 | 证据 | 结论 |
|---|---|---|
| 幂等键查询 | `Index Scan using uk_order_customer_idempotent`，0.165ms | 索引有效 |
| stock 按 SKU 查询 | `Index Scan using uk_stock_sku_wh`，0.094ms | 索引有效（小表可能选 Seq，但索引存在） |
| 地址查询 | 主键 | 正常 |
| 数据库死锁 | `deadlocks=0` | 无死锁 |
| 临时文件 | `temp_files=0` | 无大排序落盘 |
| 缓存命中 | `blks_hit/(blks_hit+blks_read) ≈ 99.999%` | 内存命中良好 |

### 5.7 其他潜在问题

- **订单号生成**：`AtomicInteger` + 秒级时间戳 + 4 位序号，单 JVM 每秒最多 10,000；300 并发无问题，但更高吞吐/多实例会撞唯一索引。建议数据库序列或雪花 ID。
- **幂等键并发**：两个相同 `idempotentKey` 同时提交时，先查后插存在竞态；唯一索引会拦住一个，但当前未捕获 `DuplicateKeyException` 转成幂等成功，可能返回 500。
- **日志**：每单 `log.info` + 访问日志，7,651 单/20s 约 382 条/s，同步 appender 会成为次要 I/O 压力；建议异步日志/采样。
- **长事务**：`@Transactional` 包住了配置查询、会员查询等非核心写操作，持有连接时间偏长；建议把配置/会员查询移出事务或缓存。

## 6. 优化建议与优先级

### P0：先解决连接池与线程池

| 优化 | 建议值 | 依据 |
|---|---|---|
| Hikari `maximum-pool-size` | 20~30（先 20，压测再调） | 当前 5，pending 195 |
| Hikari `minimum-idle` | 5~10 | 减少冷启动抖动 |
| Tomcat `max-threads` | 400（连接池提升后再调） | 当前 200 被打满 |
| Tomcat `accept-count` | 200~500 | 300 VU 时有约 100 排队 |

> 不要直接把连接池设为 300：数据库连接是昂贵资源，300 个连接会压垮 PostgreSQL；应按 DB CPU/内存和压测结果调。

### P1：减少 SQL 与持锁时间

1. 系统配置加 Caffeine 缓存，TTL 1~5 分钟，预计减少 3 次 SQL/单。
2. 合并 `isActive` + `maskedPhone` 为一次会员查询，预计减少 1 次 SQL/单。
3. stock 改为原子 `UPDATE ... WHERE physical-locked >= qty`，减少 1 次往返并缩短行锁持有时间。
4. 增加 `order_item(order_id)` 索引。
5. 幂等键插入冲突捕获，转为返回已有订单。
6. 订单号改为数据库序列/雪花 ID。

### P2：可观测与容量

1. 安装 `pg_stat_statements`，按 SQL 维度看总耗时、调用次数、平均耗时。
2. 增加 `order_item`、`stock_log` 到本地 exporter 的表扫描面板。
3. 增加 Hikari pending 的告警（如 >50 持续 1 分钟）。
4. 增加 Tomcat busy >80% 告警。
5. 压测数据自动化清理脚本，避免测试订单累积。
