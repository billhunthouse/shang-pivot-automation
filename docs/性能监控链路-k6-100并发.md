# 本地性能监控链路（100 并发）

> 日期：2026-11-09  
> 目标：让 k6 客户端指标、Spring Boot 服务端指标、JVM、连接池、PostgreSQL、Redis 在同一时间轴上可查，用于定位瓶颈。

## 1. 链路结构

```text
k6 (local)
  │ remote write (app=shang-pivot, env=local-perf)
  ▼
Prometheus 127.0.0.1:19090
  ▲  scrape 5s
  ├── Spring Boot Actuator 127.0.0.1:8087/actuator/prometheus
  └── metrics_exporter.py 127.0.0.1:19187/metrics
        ├── PostgreSQL 127.0.0.1:55434/shang
        └── Redis container shang-redis

Grafana 127.0.0.1:13000
  └── datasource uid: projectku-prometheus
```

## 5. 指标口径

### 5.1 客户端

- `k6_vus`：当前 VU
- `k6_http_reqs_total`：请求计数
- `k6_http_req_duration_p95/p99`：k6 Trend 统计，单位 **秒**，报告中乘 1000 转 ms
- `k6_http_req_failed` / `k6_checks_rate`

### 5.2 服务端

- `http_server_requests_seconds_count/sum`：按 URI 的 HTTP 计数和总耗时
- **注意**：当前 Actuator 暴露的是 summary，不是 histogram；无法直接算服务端 P95/P99。
  - 服务端平均耗时 = `rate(sum)/rate(count)`
  - 服务端最大耗时 = `http_server_requests_seconds_max`
  - 客户端 P95/P99 来自 k6
  - 原有仪表板中的 `histogram_quantile` 面板会为空，这是指标类型限制，不是采集失败
- `jvm_memory_used_bytes{area="heap"}`
- `jvm_gc_pause_seconds_*`
- `hikaricp_connections_active/pending/max/acquire_seconds_max`
- `tomcat_threads_busy_threads/current_threads`

### 5.3 数据库/缓存

- `pg_activity_active`：当前活跃会话
- `pg_activity_lock_wait` / `pg_locks_waiting`：锁等待
- `pg_stat_database_xact_commit/rollback`：事务提交/回滚
- `pg_table_seq_scan/idx_scan`：累计扫描次数，压测前后差值才有意义
- `redis_ops_per_sec`、`redis_connected_clients`、`redis_used_memory_bytes`

## 6. 查询与归档

```bash
START=$(cat artifacts/perf-100u/load-start-epoch.txt)
END=$(cat artifacts/perf-100u/load-end-epoch.txt)
agent_service/.venv/bin/python observability/local/query_metrics.py \
  --start "$START" --end "$END" \
  --out artifacts/perf-100u
```

输出：

- `prometheus-summary.json`：每个查询的 first/last/min/max/avg/delta
- `prometheus-*.json`：Prometheus 原始 range 结果
- `postgres-snapshot.txt`：压测后 PostgreSQL 统计
- `explain-and-indexes.txt`：关键 SQL EXPLAIN 与索引

## 7. 已知限制

- Prometheus/Grafana 与应用同机，监控自身也消耗 CPU/内存。
- 5s 采样会漏掉极短峰值；100 VU 的 Hikari pending 已采样到 7，说明真实峰值可能更高。
- 服务端没有 histogram，不能从 Actuator 直接得到服务端 P95/P99；需要后续引入 Micrometer histogram 或 OTel span metrics。
- Redis 指标通过 `docker exec redis-cli INFO` 采集，适合本地；生产应使用 redis_exporter。
- 本地数据量只有几十个 SKU/SPU，EXPLAIN 的绝对耗时很低，索引问题要结合 seq_scan 增量和代码路径判断。
