# 100 并发性能测试方案评审记录

> 评审对象：`docs/性能测试方案-k6-100并发-本地.md` v1.0  
> 评审日期：2026-11-09  
> 结论：有条件通过，按下列问题修订后执行

## 1. 评审结论

方案方向正确，但 v1.0 存在“只压客户端、缺少服务端证据”“100 VU 没有稳态窗口”“写链路容量表述容易误导”等问题。修订后可以执行。

## 2. 发现的问题与修订

| 级别 | 问题 | 风险 | 修订 |
|---|---|---|---|
| P0 | 只规划 k6 客户端指标 | 无法判断瓶颈在应用、连接池还是数据库 | 增加 Prometheus + Grafana + PostgreSQL/Redis exporter，形成客户端/应用/JVM/DB 四层链路 |
| P0 | 100 VU 只有阶梯上升，没有稳态 | 峰值样本太短，GC/连接池/缓存未稳定 | 增加 120s 100 VU 稳态窗口 |
| P1 | 写链路原计划 1 VU | 不能反映 3 个并发用户下的锁竞争 | 改为 3 VU × 30s，并明确“仅冒烟，不代表 100 并发写容量” |
| P1 | 没有明确预热 | JIT、连接池、PG 缓存会让前后数据不可比 | 基线前先执行预检 + 1 VU 热身；报告中注明冷/热状态 |
| P1 | 没有客户端指标入库方式 | 只能看终端 summary，无法与 JVM/DB 对齐时间轴 | k6 使用 `experimental-prometheus-rw`，标签 `app=shang-pivot`、`env=local-perf` |
| P1 | 没有停止条件 | 本地机器可能被压到无响应，数据也失真 | 错误率 >5%、应用 CPU 持续 >90%、Hikari pending 持续 >0 时停止并保留现场 |
| P2 | 登录场景未说明用户规模 | 10/s 容易被误解为 100 并发登录 | 明确 10 次/秒 × 60s = 约 600 次登录，是登录峰值，不是 100 VU 同时登录 |
| P2 | Grafana 数据源 UID 未确认 | 现有仪表板引用 `projectku-prometheus`，本地默认数据源会空白 | 本地 provision 数据源 UID 固定为 `projectku-prometheus` |
| P2 | 数据库指标只看压测后快照 | 无法观察峰值瞬间等待/锁 | exporter 5s 采集；报告同时保留压测前后 `pg_stat_user_tables` |
| P3 | 未说明本地数据量影响 | Seq Scan 在 47 行 SKU 上仍快，容易误判“无瓶颈” | 报告中明确“小数据量掩盖索引问题”，用 `EXPLAIN` 和代码路径做辅助判断 |

## 3. 评审后场景确认

| 场景 | 参数 | 目的 |
|---|---|---|
| 预检 | 1 次迭代 | 校验登录、地址、SKU 池、写链路 |
| 基线 | 1 VU × 60s | 热身后的单用户基线 |
| 阶梯负载 | 20→60→100 VU，100 VU 稳态 120s | 主场景，观察拐点 |
| 登录链路 | 10/s × 60s | 登录峰值 |
| 写冒烟 | 3 VU × 30s | 写链路可用性，不测写容量 |

## 4. 通过条件

- 预检全部通过；写链路至少有 1 个可用地址和 SKU
- Prometheus 中 `up{job="shang-pivot"}==1`，k6 指标带 `app="shang-pivot"`
- 100 VU 稳态至少持续 120s
- 报告中每个瓶颈至少有“指标 + 代码/SQL 证据 + 影响”三项
- 不修改业务代码/SQL，不把本地结果外推生产

## 5. 评审签署

- 测试方案：有条件通过
- 监控方案：通过
- 写链路范围：通过（冒烟）
- 优化动作：本轮不做
