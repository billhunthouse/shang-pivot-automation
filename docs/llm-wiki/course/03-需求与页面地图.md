# 需求与页面地图：从 52 条需求到 41 个页面

## 本节目标

- 区分 V1、V2、EXT 三类需求；
- 从需求 ID 找到页面路由；
- 从页面路由反查它调用的接口。

## 1. 需求目录

`data/requirements.json` 共 52 条：

| 前缀 | 数量 | 含义 |
|---|---:|---|
| `V1-FR-*` | 24 | 后台管理：权限、商品、库存、订单、售后、配置 |
| `V2-FR-*` | 26 | C 端交易 + 管理端增强：会员、运营位、评价、导出 |
| `EXT-*` | 2 | 扩展能力：C 端 AI 助手、评价商家回复 |

读需求 ID 的方法：

```text
V2-FR-015
│  │   └── 该版本内序号
│  └────── FR = Functional Requirement
└───────── V2 = 第二个版本
```

`EXT` 表示不在原 PRD 版本内、由后续迭代补充的能力。

## 3. 追溯矩阵怎么用

`05-traceability-matrix.md` 的一行：

```text
V2-FR-015 发表评价与详情页展示
页面：page:mall:/product/:spuId
接口：DELETE /api/favorites/{spuId}
      GET /api/products/{spuId}
      POST /api/cart/items
      POST /api/favorites/{spuId}
```

注意：这是**页面实际调用集合**，不等于需求的全部接口。评价提交真正走 `POST /api/reviews`，但矩阵里没列出来，因为页面映射是启发式，漏了间接调用。

> 结论：矩阵用来缩小范围，最终以页面源码和 `apis.json` 为准。

## 4. 实例：评价功能跨了哪几层

| 层 | 证据 |
|---|---|
| 需求 | `V2-FR-015` 发表评价与详情页展示 |
| 需求 | `V2-FR-025` 评价管理 |
| 扩展 | `EXT-REVIEW-REPLY-001` 商家回复 |
| 页面 | `page:mall:/product/:spuId`、`page:mall:/orders/:id`、`page:admin:/reviews` |
| 接口 | `POST /api/reviews`、`GET /api/products/{spuId}`、`GET /admin/reviews`、`PUT /admin/reviews/{id}/reply` |
| 代码 | `StorefrontController#createReview`、`ReviewAdminService#reply` |
| 表 | `commerce.review`（含 `merchant_reply`、`replied_at`） |

这条链能直接支撑三件事：

1. 新需求影响分析；
2. API + UI 用例设计；
3. 线上问题定位。

## 5. 常见误区

| 误区 | 正确做法 |
|---|---|
| 把页面路由当成需求 ID | 两者是多对多 |
| 只看看得见的按钮 | 间接调用的接口要读源码 |
| 认为管理端页面都在 `/admin` 后端 | 前端路由前缀和管理端 API 前缀不是一回事 |
| 忽略 `(global)` 浮窗 | AI 助手没有独立路由，但也是页面入口 |
