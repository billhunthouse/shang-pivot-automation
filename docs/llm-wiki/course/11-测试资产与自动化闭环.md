# 测试资产与自动化闭环：从用例到 Allure

## 本节目标

- 说清仓库里有哪些测试资产；
- 知道每类资产适合测什么；
- 能跑通一次 API + UI + Allure；
- 理解失败自动建 Bug 的闭环。

## 1. 测试资产地图

| 目录 | 内容 | 技术 |
|---|---|---|
| `api_testcases/` | 接口契约、库存驱动、Allure | pytest + requests |
| `pytest_automation/` | 业务自动化、数据工厂、禅道同步 | pytest |
| `automation/` | BDD 场景 | Java + Cucumber |
| `shang-mall` / `shang-admin-web` | UI 用例 | Playwright |
| `observability/k6/` | 性能脚本 | k6 |
| `docs/llm-wiki/` | 知识库与课件 | Python 生成器 |

## 2. 测试金字塔

```text
        UI（少）
      /        \
   API（中）    E2E（关键路径）
      \        /
      单元/契约（多）
```

本项目重点：

- API 契约与库存驱动用例；
- 关键 UI 跨端闭环；
- k6 性能基线；
- 不做大规模单元测试（演示项目）。

## 3. 一次完整的自动化闭环

```bash
# API + UI
cd api_testcases
pytest -q

# 生成 Allure
allure generate artifacts/allure-results -o artifacts/allure-report --clean
allure open artifacts/allure-report
```

评价商家回复的实战结果：

```text
8 passed（API 7 + UI 1）
Allure 100%
```

## 4. 失败自动同步禅道

流程：

```text
pytest 失败
→ 收集断言、请求、响应、截图、steps
→ 调禅道 MCP 创建 Bug
→ 附件上传
→ 回写用例执行结果
```

关键设计：

- 失败信息结构化，不只是一行异常；
- 截图和 steps 作为附件；
- Bug 标题包含用例 ID，便于去重；
- 网络失败不误报为产品 Bug。

## 5. 性能测试

```text
k6 100 VU 阶梯
→ Prometheus / Grafana
→ P95、错误率、吞吐
→ 瓶颈定位到 SQL/连接池/锁
```

注意：Actuator HTTP 指标是 summary，不能直接算服务端 P95；要用 histogram 或网关指标。

## 6. 评测闭环

Agent 评测关注：

| 维度 | 指标 |
|---|---|
| 正确性 | 答案是否命中标准答案 |
| 引用 | 是否引用知识库 |
| 工具调用 | 是否调对工具、参数正确 |
| 延迟 | P50/P95 |
| 成本 | token 数 |
| 安全 | 越权、注入、敏感信息 |

## 7. 常见误区

| 误区 | 正确做法 |
|---|---|
| 只写 UI 用例 | API 覆盖边界和并发，UI 只做关键路径 |
| 用例依赖种子数据 | 专用 fixture + 清理 |
| 失败只存日志 | 存请求/响应/截图/steps |
| 性能只看平均值 | 看 P95/P99 和错误率 |
| 评测只看最终答案 | 同时看检索和工具调用 |

## 练习

1. 跑一次 `api_testcases`，打开 Allure 报告。
2. 找一条失败用例，检查是否包含请求、响应、截图。
3. 为“评价商家回复”补一条并发用例的设计。
