# 后续功能路线图

## 1. 评估维度

| 维度 | 说明 |
|---|---|
| 用户价值 | 是否减少找答案/做分析的时间 |
| 实现成本 | 人日与依赖 |
| 数据要求 | 是否需要新数据/标注 |
| 风险 | 过期、误答、权限、维护成本 |

## 3. 三期计划

### 第一期：可学、可查（1-2 周）

- 学习中心页（已完成）；
- 进度与完成标记；
- 课程上传知识库；
- 召回测试入口。

### 第二期：可分析、可验证（3-4 周）

- 需求影响分析工作流；
- 图谱节点跳课程/接口；
- 召回评测集与看板；
- 失败样本回流。

### 第三期：可运营、可扩展（1-2 月）

- 代码变更触发 wiki 增量更新；
- 过期检测与负责人提醒；
- 多项目模板；
- MCP 暴露图谱查询。

## 4. 需求影响分析工作流设计

```text
输入：需求描述 + 目标端
  → 检索 requirement/rule
  → 找相似需求
  → 页面候选
  → 接口复用/扩展/新增
  → Controller/Service/表
  → 风险清单
  → 输出 Markdown/表格
```

验收：

- 每条结论带 `id` 引用；
- 无法确认的标“待验证”；
- 不把 wiki 当唯一真值。

## 5. 过期检测

```text
代码变更（git diff）
  → 提取 Controller/Service/表
  → 对比 wiki 索引
  → 标记受影响 chunk
  → 生成待更新列表
```

指标：

- 过期 chunk 比例；
- 平均修复时长；
- 影响分析引用过期 chunk 的比例。

## 6. 不建议现在做

| 功能 | 原因 |
|---|---|
| 自建向量数据库 | pgvector 够用，维护成本高 |
| 全自动改代码 | 风险高，先做分析与建议 |
| 大规模爬取外部文档 | 噪声大，先保证内部真值 |
| 复杂权限模型 | 当前演示级，先把项目级隔离做好 |

## 7. 一句话

> 先把“找得到、看得懂、验证得了”做扎实，再谈自动化和智能化。
