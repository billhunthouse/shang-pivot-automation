## 2. 图谱长什么样

```text
requirement ──has_page──▶ page ──calls_api──▶ api
     │                                          │
     └──────────has_api────────────────────────┘
                                                │ handled_by
                                                ▼
                                           controller
                                                │ calls_service
                                                ▼
                                             service
                                                │ accesses_table
                                                ▼
                                              table
```

## 3. 一跳/两跳影响分析

问题：**给评价增加“商家回复”要改哪里？**

```text
起点：EXT-REVIEW-REPLY-001
一跳：page:admin:/reviews、page:mall:/product/:spuId
两跳：GET /admin/reviews、PUT /admin/reviews/{id}/reply、GET /api/products/{spuId}
三跳：ReviewAdminService、AdminOpsController、commerce.review
```

输出影响表：

| 层 | 影响项 | 复用/修改/新增 |
|---|---|---|
| 表 | `commerce.review` | 新增两列 |
| 接口 | `PUT /admin/reviews/{id}/reply` | 新增 |
| 服务 | `ReviewAdminService.reply` | 新增 |
| 页面 | 管理端评价列表、C 端商品详情 | 修改 |
| 测试 | API 7 条 + UI 1 条 | 新增 |

## 4. 常用 Cypher

```cypher
// 某需求涉及的接口
MATCH (r:Requirement {id:'V2-FR-015'})-[:REQUIREMENT_HAS_API]->(a:Api)
RETURN r.label, a.label;

// 某页面调用的接口及落表
MATCH (p:Page {id:'page:mall:/product/:spuId'})-[:PAGE_CALLS_API]->(a:Api)
OPTIONAL MATCH (a)-[:ACCESSES_TABLE]->(t:Table)
RETURN p.label, a.label, collect(t.label);

// 某接口的完整下钻
MATCH path=(a:Api {id:'api:GET:/api/products/{spuId}'})-[*1..3]->(n)
RETURN path LIMIT 20;
```

导入 Neo4j：

```bash
cat docs/llm-wiki/data/graph.cypher | cypher-shell -u neo4j -p '<password>'
```

## 5. 图谱的边界

- 关系是**静态结构**，不是运行时调用次数；
- 页面→接口来自 Vue import 启发式，间接调用可能漏；
- 需求→页面/接口按模块映射，跨模块需求可能不完整；
- 新增 API/页面/需求后必须重跑生成器。

运行时链路请看 SkyWalking、`call-graph.json` 或访问日志。

## 6. 图谱的三个实用场景

1. **新人问答**：这个页面调了哪些接口？
2. **影响分析**：改这张表会波及哪些需求？
3. **测试选型**：一条需求至少要覆盖哪些页面和接口？
