# 面试表达与练习：把项目讲成能力

## 本节目标

- 用 3 分钟讲清项目；
- 准备 5 个可追问的技术故事；
- 回答“你做了什么”而不是“项目有什么”；
- 用 7 天计划补齐短板。

## 1. 三分钟项目介绍

```text
背景：这是一个分版本演进的电商全栈项目，V1 后台、V2 商城、V3 接入 AI 助手。
架构：Spring Boot 模块化单体 + Vue 双端 + PostgreSQL/Redis + LangGraph Agent。
我的工作：
  1. 建了一套 LLM-wiki，把 52 条需求、41 个页面、137 个接口、31 张表连成图谱；
  2. 基于图谱做需求影响分析和用例设计；
  3. 做 API + UI 自动化，接入 Allure 和禅道；
  4. 做过性能测试和 AI Agent 评测。
结果：新需求影响分析从半天缩短到 10 分钟；评价回复功能 8 条用例全绿；
      发货 ID 精度 Bug 从日志定位到修复并补了规范。
```

## 2. 五个 STAR 故事

### 故事一：LLM-wiki 知识图谱

- Situation：文档、接口、代码割裂，新人问“改哪里”答不上来；
- Task：建一套可追溯的知识库；
- Action：设计五层模型，写生成器，产出 309 节点/964 边图谱；
- Result：影响分析可下钻到 Controller 和表。

### 故事二：评价商家回复

- Situation：商家无法公开回复评价；
- Task：管理端回复 + C 端展示；
- Action：影响分析 → 改表/接口/UI → 8 条自动化；
- Result：API 7 + UI 1 全绿，Allure 100%。

### 故事三：发货“订单不存在”

- Situation：商家端发货 404；
- Task：定位并修复；
- Action：日志 ID 与 DB ID 对比，发现 JS 精度丢失；
- Result：字符串 ID 全链路修复，补防复发规范。

### 故事四：性能测试

- Situation：不知道系统能扛多少并发；
- Task：做 100 VU 基线；
- Action：k6 + Prometheus/Grafana + SQL/连接池分析；
- Result：找出 N+1、连接池、锁竞争等瓶颈。

### 故事五：失败自动建 Bug

- Situation：自动化失败后信息散落；
- Task：失败自动同步禅道；
- Action：结构化失败信息 + 截图 + steps + MCP；
- Result：失败可追踪、可复现、可统计。

## 3. 高频问题

### Q1：为什么用模块化单体，不用微服务？

答：演示项目需要一键启动、本地事务简单、调试链路短；但模块边界按可拆分设计，跨模块只走 `*-api`，未来可拆。

### Q2：LLM-wiki 和普通文档有什么区别？

答：五层结构 + 稳定 ID + 关系边，能从一个问题跳到文件/接口/表；普通文档是线性叙述。

### Q3：怎么保证 wiki 不过期？

答：生成器 + 时间戳 + 真值顺序；新增接口/页面/需求后重跑 `build_wiki.py` 和 `build_graph_view.py`；代码永远优先。

### Q4：RAG 召回不准怎么办？

答：先看切片粒度和元数据，再看 top-k/过滤，最后看 prompt 是否强制引用；用 20 条评测集量化。

### Q5：怎么测订单状态机？

答：按转移表设计：每个合法转移、每个非法转移、重复操作幂等、并发、库存/流水副作用。

### Q6：雪花 ID 为什么要字符串？

答：19 位超过 JS 安全整数，`Number()` 会丢末位；后端序列化为字符串，前端全程字符串。

### Q7：售后“退款中”为什么测不到？

答：通过审核时同一事务写 `REFUNDING` 再写 `COMPLETED`，外部不可观测；测试应断言最终 `COMPLETED`。

### Q8：接口测试和 UI 测试怎么分工？

答：API 覆盖契约、边界、权限、并发、数据副作用；UI 只覆盖关键用户路径和跨端展示。

### Q9：性能瓶颈怎么定位？

答：先看 P95/错误率，再看 Tomcat/Hikari/JVM/PostgreSQL/Redis 指标，最后看慢 SQL 和锁。

### Q10：AI Agent 怎么评测？

答：正确性、引用、工具调用、延迟、成本、安全六个维度；用固定评测集和 trace。
