# 从代码到知识库：LLM-wiki 的设计动机

## 本节目标

- 说清“文档很多但找不到答案”的根因；
- 理解 LLM-wiki 的五层模型和真值顺序；
- 知道 wiki 的生成物、更新方式和边界。

## 1. 普通文档的三个断裂

### 断裂一：需求与实现脱节

PRD 说“支持评价”，但没说：

- 哪个页面发起？
- 调哪个接口？
- 评价写哪张表？
- 商家回复改哪个字段？
- 隐藏评价后 C 端还显示吗？

### 断裂二：接口与页面脱节

页面里 import 了 8 个 API 函数，接口文档却按 Controller 分组。新人很难回答“商品详情页到底调了什么”。

### 断裂三：代码与数据脱节

`OrderService.ship()` 改了订单状态，还扣库存、写流水、生成出库单。只看 Service 名字看不出来。

## 2. 五层知识模型

LLM-wiki 把系统拆成五层，每层都有稳定 ID：

```text
requirement  V2-FR-015 发表评价
    │ has_page
    ▼
page         page:mall:/product/:spuId
    │ calls_api
    ▼
api          GET /api/products/{spuId}
    │ handled_by
    ▼
controller   StorefrontController#productDetail
    │ calls_service
    ▼
service      CatalogReadService
    │ accesses_table
    ▼
table        commerce.spu / sku / stock / review
```

这样做的好处：

1. 任何问题都能定位到某一层，而不是“全栈都看看”；
2. 层与层之间有边，可以做一跳、两跳影响分析；
3. LLM 检索时能拿到结构化上下文，减少编造。

## 3. 真值顺序

出现冲突时，按这个顺序判断：

1. **运行代码**：Controller、Service、SecurityConfig、Mapper、SQL；
2. **As-built 业务规则**：`docs/06-baseline/02-业务规则与状态机.md`；
3. **生成物**：`call-graph.json`、`endpoint-model.json`、OpenAPI；
4. **PRD**：V1/V2 需求文档；
5. **wiki**：导航和自动映射。

> 记住：wiki 是地图，不是领土。地图过期时，以代码为准。

## 4. wiki 的生成物

| 文件 | 内容 | 谁消费 |
|---|---|---|
| `data/apis.json` | 137 个端点、鉴权、Controller/Service/表 | 脚本、LLM |
| `data/pages.json` | 41 个页面与调用接口 | 影响分析 |
| `data/requirements.json` | 52 条需求 | 需求检索 |
| `data/graph.json` | 309 节点、964 边 | 图谱可视化 |
| `data/chunks.jsonl` | 242 条 RAG 切片 | 召回 |
| `graph.html` | 交互式分层图 | 人 |
| `graph.cypher` | Neo4j 导入 | 图数据库 |

## 5. 生成流程

```bash
# 1. 扫描代码、文档、OpenAPI，重建 wiki 索引
python3 docs/llm-wiki/scripts/build_wiki.py

# 2. 基于索引重建知识图谱
python3 docs/llm-wiki/scripts/build_graph_view.py

# 3. 启动本地图谱页面
python3 -m http.server 9092 --bind 127.0.0.1 --directory docs/llm-wiki
```

注意：页面 import 映射是启发式，间接调用可能漏；新增接口后必须重跑生成器。

## 6. 常见误区

| 误区 | 正确做法 |
|---|---|
| “PRD 写了就是实现了” | 回 Controller/Service 确认 |
| “页面调用的接口就是全部接口” | 看 `apis.json` 和调用链 |
| “图谱关系等于运行时调用次数” | 图谱是静态结构，运行时看 SkyWalking |
| “wiki 可以替代测试” | wiki 帮你选范围，验证仍要跑代码和数据 |
