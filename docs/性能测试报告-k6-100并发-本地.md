# 尚品汇本地 100 并发用户性能测试报告

> 日期：2026-11-09  
> 环境：本地，Spring Boot 4.1.1 / Java 21 / PostgreSQL 16 / Redis 7  
> 压测工具：k6 v2.3.0  
> 约束：不修改业务代码和 SQL；本轮只测量、监控、定位，不做优化  
> 原始数据：`artifacts/k6-100u/`、`artifacts/perf-100u/`

## 1. 结论摘要

100 VU 阶梯负载完成，功能层面全部通过：

| 指标 | 结果 |
|---|---:|
| 总请求数 | 50,681 |
| 平均 RPS（含阶梯升降） | 140.47 |
| 100 VU 稳态 RPS | 192.20 |
| 峰值 RPS（1 分钟窗口） | 198.74 |
| P95（全场景） | 29.12 ms |
| P99（全场景） | 63.19 ms |
| **P95（100 VU 稳态）** | **76.10 ms** |
| **P99（100 VU 稳态）** | **128.73 ms** |
| 最大响应时间 | 219.06 ms |
| HTTP 失败 | 0 |
| 断言通过 | 101,356 / 101,356 |

**主要瓶颈不是 Tomcat 线程，也不是 JVM/Redis，而是 HikariCP：**

- Hikari 最大连接数只有 **5**
- 100 VU 期间 `pending` 峰值 **7**
- `acquire` 最大等待 **69ms**
- 同期 Tomcat busy 峰值只有 **13 / 200**
- PostgreSQL 活跃会话峰值 3，锁等待 0

说明请求已经打满数据库连接池，应用线程在等连接；当前响应时间仍低，是因为本地数据量小、查询本身很快，但连接池已没有余量。

## 5. 瓶颈定位

### P0：HikariCP 只有 5 个连接，100 VU 出现 pending

**证据：**

- `hikaricp_connections_max=5`
- `hikaricp_connections_active` 峰值 5
- `hikaricp_connections_pending` 峰值 7
- `hikaricp_connections_acquire_seconds_max=69ms`
- 同期 Tomcat busy 仅 13，说明不是 Web 线程不够
- PostgreSQL 活跃会话仅 3，锁等待 0，说明数据库本身未饱和

**判断：** 应用在 100 VU 的短时突发下连接池容量不足，后续请求等待连接。当前 P95 仍低是因为本地数据量小、SQL 很快；数据量或写链路放大后会先在这里恶化。

### P1：`toCard()` N+1 + `sku` 缺组合索引

**代码证据：**

- `CatalogReadService.toCard()` 对每个 SPU 执行一次 `skuMapper.selectList(spu_id + status)`，列表 20 条即 20 次 SKU 查询。
- `CatalogReadService.detail()` 对每个 SKU 再执行一次 `stock` 查询。
- `commerce.sku` 只有主键和条码索引，没有 `(spu_id, status, deleted)` 组合索引。
- `commerce.stock` 只有 `(sku_id, warehouse_id)` 唯一索引，`available()` 使用 `sku_id + LIMIT 1`。

**SQL 证据：**

```text
EXPLAIN sku by spu_id/status:
Seq Scan on sku
  Filter: ((NOT deleted) AND (spu_id = 246) AND status = 'ENABLED')
  Rows Removed by Filter: 44
  Execution Time: 0.042 ms
```

当前表只有 47 行，Seq Scan 仍然很快；但压测 6 分钟 `sku` seq_scan 增加 **207,820 次**，说明查询模式会随数据量放大。

### P1：`spu` 列表/搜索缺组合索引，LIKE 前后通配

**证据：**

- `spu` 只有主键和 `schedule_on_at` 索引，没有 `(status, deleted, sold_count/id)` 或 `(category_id, status, deleted)` 组合索引。
- 搜索使用 `name LIKE '%keyword%' OR subtitle LIKE '%keyword%'`，普通 B-tree 无法高效支持。
- 压测期间 `spu` seq_scan 增加 **85,123 次**。
- `EXPLAIN` 列表和搜索均为 Seq Scan；当前 32 行，执行时间约 0.06ms。

### P2：首页是读链路最重接口

- 首页 P95 80.25ms、P99 124.68ms、最大 219.06ms。
- 商品列表 P95 29.71ms、搜索 12.35ms、详情 24.24ms。
- 首页包含品牌、运营位、推荐流等多段查询，且没有缓存；在 100 VU 下先于其他读接口放大。

### P2：写链路风险尚未验证

- 本轮只跑 3 VU 写冒烟，全部成功。
- `OrderSubmitService.submit` 使用 `FOR UPDATE` 锁库存并写 stock log。
- Hikari 最大 5，写事务持续时间和热点 SKU 行锁可能在 100 并发写时造成排队；本轮没有验证，不能据此判断写容量安全。

## 6. 本轮未做的优化（按要求）

以下只作为后续建议，本轮没有改代码或 SQL：

1. 为 `commerce.sku` 增加 `(spu_id, status, deleted)` 组合索引。
2. 把 `toCard()` 的逐 SPU SKU 查询改为一次批量查询。
3. 为 `spu` 列表/搜索补组合索引；搜索考虑 pg_trgm 或搜索引擎。
4. 首页品牌/运营位/推荐流增加短 TTL 缓存。
5. 按数据库实际承载能力调整 Hikari 最大连接数，并补连接池等待告警。
6. 引入 Micrometer histogram/OTel span metrics，服务端 P95/P99 不再依赖 summary 估算。
7. 单独设计写链路容量测试（独立数据、热点 SKU、库存回滚方案）。

## 8. 限制

- 本地数据量小，索引和 N+1 的绝对延迟被掩盖；用扫描增量 + EXPLAIN 判断趋势。
- k6 与应用/数据库同机，客户端 CPU 与服务端资源竞争，绝对吞吐不能外推生产。
- 100 VU 是虚拟用户，不等于 100 个真实用户的行为组合；真实还包括弱网、长连接、多端、推送等。
- 服务端 Actuator 暴露的是 summary，不能直接计算服务端 P95/P99；本报告用 k6 P95/P99 + 服务端平均/最大耗时交叉判断。
- 写链路仅 3 VU 冒烟，未验证库存行锁、Hikari 5 连接下的 100 并发写。
- 监控链路为本地 Docker + Python exporter，生产应使用独立 exporter、长期存储和告警。
