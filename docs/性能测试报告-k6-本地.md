# 尚品汇电商平台 k6 本地性能测试报告

> 日期：2026-11-05  
> 环境：本地开发环境（非服务器、非生产）  
> 工具：k6 v2.3.0  
> 原则：只测试、只分析，不做代码优化

## 1. 结论摘要

本轮完成了预检、基线、负载、压力、登录和写链路冒烟，共 6 组场景。所有场景阈值均通过，未出现 HTTP 失败或业务断言失败。

| 场景 | 请求数 | RPS | P95 | P99 | 失败率 |
|---|---:|---:|---:|---:|---:|
| 基线 1 VU / 30s | 63 | 2.03 | 41.23ms | 63.41ms | 0% |
| 负载 5→20→40 VU / 100s | 8,405 | 83.82 | 22.14ms | 38.25ms | 0% |
| 压力 20→50→80 VU / 50s | 20,273 | 403.27 | 9.71ms | 17.76ms | 0% |
| C 端登录 5/s / 20s | 100 | 4.80 | 15.78ms | 17.42ms | 0% |
| 管理端登录 2/s / 15s | 31 | 1.92 | 119.77ms | 123.23ms | 0% |
| 写链路 1 VU / 10s | 64 | 5.98 | 22.06ms | 23.75ms | 0% |

核心判断：

1. **本地读链路没有被打出容量拐点**。80 VU 下仍为 0 错误，P95 低于 10ms；但这是小数据量 + 同机压测结果，不能外推到生产。
2. **首页是读链路中最重的接口**。40 VU 下 P95 48.5ms，高于列表（22.1ms）、详情（20.3ms）、搜索（12.6ms）。
3. **最大静态风险是 `CatalogReadService.toCard` 的 N+1 查询**：每个 SPU 单独查一次 SKU；首页 feed 20 条就是 20 次 SKU 查询。
4. **数据库索引与代码查询不匹配**：`commerce.sku` 只有主键和条码索引，没有 `(spu_id, status, deleted)` 索引；`EXPLAIN` 显示按 `spu_id + status` 查询走 Seq Scan。
5. **管理端登录是 CPU 型接口**：P95 119.8ms，约为 C 端登录（15.8ms）的 7.6 倍，符合 BCrypt 密码校验成本。
6. **写链路只做了单 VU 冒烟**，不能据此判断下单/库存并发能力；`FOR UPDATE` + 库存更新存在热点 SKU 锁竞争风险。

## 6. 代码与 SQL 瓶颈分析

### 6.1 P0：`toCard` N+1 + `sku` 缺索引

代码路径：`CatalogReadService.toCard`

```java
List<Sku> skus = skuMapper.selectList(new LambdaQueryWrapper<Sku>()
        .eq(Sku::getSpuId, spu.getId())
        .eq(Sku::getStatus, "ENABLED"));
```

每次卡片组装都单独查一次 SKU：

- `/api/home`：feed 20 条 → 20 次 SKU 查询；
- `/api/products`：当前页 20 条 → 20 次 SKU 查询；
- `/api/search`：结果页每条 → 一次 SKU 查询。

数据库证据：

```text
commerce.sku：seq_scan = 105,030，idx_scan = 9
commerce.spu：seq_scan = 39,611，idx_scan = 1,362
```

`sku` 现有索引：

```text
sku_pkey (id)
uk_sku_bar_code (bar_code) WHERE ...
```

没有 `(spu_id, status, deleted)` 索引。`EXPLAIN`：

```text
Seq Scan on sku
  Filter: ((NOT deleted) AND (spu_id = 101) AND (status = 'ENABLED'))
  Rows Removed by Filter: 44
  Execution Time: 0.043 ms
```

当前只有 47 行 SKU，Seq Scan 仍然很快；一旦 SKU 增长到万级，这个 N+1 + 全表扫描会线性放大。

### 6.2 P1：`spu` 列表/搜索缺少组合索引

`productPage` 条件：

```java
q.eq(Spu::getStatus, "ON")
 .eq(categoryId != null, Spu::getCategoryId, categoryId);
```

`spu` 只有主键和 `schedule_on_at` 索引，没有 `(status, deleted, sold_count/id)` 或 `(category_id, status, deleted)` 组合索引。`EXPLAIN` 显示列表查询走 Seq Scan（32 行时成本很低）。

`search` 使用：

```java
.and(w -> w.like(Spu::getName, keyword)
          .or().like(Spu::getSubtitle, keyword))
```

前后通配 `%keyword%` 无法使用普通 B-tree；数据量上来后会全表扫描。当前 32 行，搜索 P95 仍只有 12.6ms，但这是数据量小掩盖了风险。

### 6.3 P1：购物车 `toItemVo` N+1

`CartService.getCart` 对每个购物车项执行：

1. `skuMapper.selectById`
2. `spuMapper.selectById`
3. `stockMapper.selectOne`

即每个条目 3 次查询。购物车 10 条商品就是约 30 次查询。40 VU 下 `/api/cart` P95 7.93ms 尚可，但购物车条目增长或数据库变大后会放大。

### 6.4 P2：详情页库存查询

`CatalogReadService.detail` 对每个 SKU 调用 `available()`：一次 SKU 列表查询 + 每个 SKU 一次 stock 查询。`stock` 的现有唯一索引是 `(sku_id, warehouse_id) WHERE deleted=false`，但 `availableStock` 使用 `sku_id` + `ORDER BY id LIMIT 1`，`EXPLAIN` 在 47 行数据下选择 Seq Scan（0.098ms）。数据量上来后应按实际查询形态补 `(sku_id, deleted)` 或去掉无意义的 `ORDER BY id`。

### 6.5 P2：首页多段查询

`CatalogReadService.home` 一次调用包含：

- 品牌 `site_brand`；
- 运营位 `home_slot` + 每个 slot 的 `home_slot_item`；
- 每个 slot 的 SPU 批量查询 + SKU 最低价查询；
- `system_config` 读取 feed 排序；
- feed 分页 + 每条 `toCard` 的 SKU 查询。

这解释了 `/api/home` 在 40 VU 下 P95 48.5ms，明显高于其他读接口。短期可缓存品牌/运营位/feed；中期应把卡片 SKU 聚合改成批量查询。

### 6.6 P2：下单库存锁与 Hikari 5 连接

`OrderSubmitService.submit` 对每个下单行执行：

```java
stockMapper.selectOne(... .last("LIMIT 1 FOR UPDATE"))
stockMapper.updateById(stock)
stockLogMapper.insert(stockLog)
```

同一 SKU 高并发下单会在库存行锁上排队；本轮只跑了 1 VU，未验证锁竞争。Hikari 最大连接数仅 5，写并发放大后 `pending` 可能上升，应作为后续写容量测试的第一观察项。

### 6.7 其他

- `SystemConfigApiImpl.getValue` 每次查 `identity.system_config`；首页/下单多次调用，可考虑缓存。
- `HomeSlotService.listForStorefront` 按 slot 循环查询 item；`home_slot_item(slot_id, sort)` 索引有效，`EXPLAIN` 为 Index Scan。
- `order` 有 `(customer_id, created_at)` 索引，订单列表路径相对健康。

## 7. 瓶颈优先级

| 优先级 | 瓶颈 | 证据 | 影响 |
|---|---|---|---|
| P0 | `toCard` 每个 SPU 单独查 SKU | 代码 + `sku` seq_scan 105,030 | 首页/列表/搜索随商品数量线性放大 |
| P0 | `sku` 缺 `(spu_id,status,deleted)` 索引 | EXPLAIN Seq Scan | N+1 的每次查询都是全表扫描 |
| P1 | `spu` 列表/搜索缺组合索引 | seq_scan 39,611 | 商品增长后列表/搜索变慢 |
| P1 | 购物车每项 3 次查询 | 代码路径 | 购物车条目多时放大 |
| P2 | 详情每个 SKU 查 stock | 代码 + stock seq_scan 5,726 | SKU 多时详情变慢 |
| P2 | 首页多段查询/无缓存 | home P95 最高 | 首页峰值成本最高 |
| P2 | 下单 `FOR UPDATE` 热点行锁 | 代码路径 | 高并发写可能排队 |
| P2 | Hikari max=5 | actuator 指标 | 写并发/长事务风险 |
| P2 | 管理端 BCrypt 登录 | P95 119.8ms | 登录风暴 CPU 成本高 |

## 8. 建议（本轮不实施代码优化）

### 8.1 数据库索引

```sql
-- 最高优先级：支撑 toCard / 详情 / 最低价
CREATE INDEX CONCURRENTLY idx_sku_spu_status
ON commerce.sku (spu_id, status)
WHERE deleted = false;

-- 列表页按状态/销量分页
CREATE INDEX CONCURRENTLY idx_spu_status_sold
ON commerce.spu (status, sold_count DESC, id)
WHERE deleted = false;

-- 分类页
CREATE INDEX CONCURRENTLY idx_spu_category_status
ON commerce.spu (category_id, status, id)
WHERE deleted = false;

-- 库存按 SKU 查询
CREATE INDEX CONCURRENTLY idx_stock_sku
ON commerce.stock (sku_id)
WHERE deleted = false;
```

索引上线前用 `EXPLAIN (ANALYZE, BUFFERS)` 对比，避免无效索引。

### 8.2 代码层（后续任务）

1. `toCard` 改为批量查 SKU，按 `spuId` 分组后组装；
2. `CartService.toItemVo` 批量查 SKU/SPU/stock；
3. `HomeSlotService` 减少按 slot 的循环查询，批量取 items；
4. 首页品牌/运营位/feed 加短 TTL 缓存；
5. `SystemConfig` 加缓存；
6. 搜索改为前缀/全文/trigram，避免 `%keyword%`；
7. 下单库存锁改为原子更新或乐观锁，减少热点行等待；
8. 压测写链路后再决定 Hikari 连接数，不要盲目调大。

## 9. 本轮测试边界

- 本地环境，k6 与后端同机；
- 数据量很小（32 SPU / 47 SKU），Seq Scan 当前仍快；
- 未测 Nginx、公网、TLS、跨机器网络；
- 未做高并发写、库存竞争、长时间 soak；
- 写链路只 1 VU，10 次下单，不能作为容量结论；
- 压力测试在负载测试之后执行，JIT/缓存已热，不能直接比较 40 VU 与 80 VU 的绝对延迟。
