# 尚品汇本地 100 并发用户性能测试方案

> 版本：v1.1（已评审修订）  
> 日期：2026-11-09  
> 范围：本地环境，仅观测和定位，不修改业务代码/SQL  
> 目标：模拟约 100 个并发用户，验证系统在本地数据量下的响应、稳定性和资源使用，定位瓶颈

## 1. 测试目标

1. 验证 100 个并发用户持续浏览时，C 端核心读链路的吞吐、P95/P99、失败率。
2. 验证登录、购物车、订单查询等受保护链路在 100 VU 混合流量下的表现。
3. 用 JVM、Tomcat、HikariCP、PostgreSQL、Redis 指标判断瓶颈在应用、连接池还是数据库。
4. 用单 VU 写链路冒烟确认下单/支付链路仍可用；不在本轮验证高并发写容量。
5. 产出可复现的脚本、原始指标、监控查询和瓶颈证据。

## 2. 被测系统与环境

| 项 | 配置 |
|---|---|
| 应用 | Spring Boot 4.1.1 / Java 21，`127.0.0.1:8086` |
| Actuator | `127.0.0.1:8087/actuator/prometheus` |
| 前端 | 商城 `127.0.0.1:5174`，管理端 `127.0.0.1:5173`（本轮压 API） |
| 数据库 | PostgreSQL 16 + pgvector，`127.0.0.1:55434/shang` |
| 缓存 | Redis 7，`127.0.0.1:56379` |
| 压测工具 | k6 v2.3.0，本地执行 |
| 监控 | Prometheus + Grafana（本地容器），k6 remote write |
| 资源限制 | k6、应用、PostgreSQL、Prometheus 同机，存在资源竞争 |

## 3. 用户模型

浏览型混合负载（沿用并复核 `observability/k6/browse-load.js`）：

| 行为 | 比例 | 说明 |
|---|---:|---|
| 商品列表 | 40% | 首页/分类瀑布流，随机页码、页大小 |
| 关键词搜索 | 25% | 帐篷/咖啡/笔记本/口红/跑步鞋/无结果词 |
| 商品详情 | 20% | 随机 SPU 详情，触发 SKU/库存查询 |
| 首页聚合 | 15% | 品牌、运营位、推荐流，最重只读路径 |
| 登录后附加读 | 概率叠加 | 类目、我的、购物车、订单、收藏 |

思考时间默认 1 秒；100 VU 稳态下预计 100–250 RPS，具体以实测为准。

## 4. 场景设计

### S1 基线

- 1 VU，60s，`THINK_TIME=1`
- 目的：确认数据、鉴权、监控标签正常，建立冷/热基线

### S2 阶梯负载（主场景）

```text
30s  → 20 VU
60s  → 60 VU
120s → 100 VU
120s → 100 VU（稳态）
30s  → 0 VU
```

- 总计约 6 分钟，峰值 100 VU
- 目的：观察吞吐、延迟拐点、连接池/线程池/数据库指标随 VU 的变化

### S3 登录链路

- 到达速率 10 次/秒，持续 60s，`LOGIN_TARGET=customer`
- 目的：验证登录接口与 JWT/Redis 写入在 100 用户登录峰值下的表现

### S4 写链路冒烟

- 3 VU，30s，`checkout-smoke.js`
- 每个 VU 独立账号，登录 → 加购 → 下单 → 沙箱支付
- 目的：确认写链路可用；不把结果外推为 100 并发写容量
- 风险：会真实创建本地订单/扣减库存，仅限本地测试库

## 5. 监控链路

```text
k6 ──remote write──► Prometheus ◄──scrape── Spring Actuator (8087)
                         ▲
                         ├──scrape── PostgreSQL/Redis exporter (19187)
                         └──scrape── Prometheus self
                              │
                              ▼
                           Grafana (13000)
```

### 5.1 客户端指标

- `k6_vus`、`k6_http_reqs_total`、`k6_http_req_duration_p95/p99`
- `k6_http_req_failed`、`k6_checks_rate`
- 接口级 Trend：home/products/search/detail/cart/orders 等

### 5.2 服务端指标

- HTTP：QPS、P95/P99、状态码、URI 维度
- JVM：heap、GC 次数/暂停、线程、类加载
- Tomcat：active/busy/queue、线程池大小
- HikariCP：active/idle/pending、acquire、timeout
- 业务：`business_failures_total`、登录/下单失败

### 5.3 数据库/缓存指标

- PostgreSQL：连接数、活跃/等待会话、事务提交/回滚、块命中/读取、死锁、临时文件
- 关键表：`sku`、`spu`、`stock`、`cart`、`order` 的 seq_scan/idx_scan/live/dead tuple
- Redis：连接数、内存、OPS、命中/未命中、evicted keys

### 5.4 采集与保留

- Prometheus scrape interval：5s
- 保留：1 天
- k6 remote write 标签：`app=shang-pivot`、`env=local-perf`
- 压测前后各采集一次 PostgreSQL `pg_stat_user_tables` 与关键 `EXPLAIN (ANALYZE, BUFFERS)`

## 6. 通过标准与熔断

| 指标 | 目标 |
|---|---|
| HTTP 失败率 | < 1% |
| 断言通过率 | > 99% |
| P95 | < 800ms |
| P99 | < 1500ms |
| 服务端 5xx | 0 |
| 应用 CPU | 持续 > 90% 时记录并考虑停止 |
| Hikari pending | 持续 > 0 时记录为容量风险 |
| 错误率突增 | > 5% 立即停止并保留现场 |

> 阈值是本地验收基线，不代表生产 SLA。数据量小，结果不能直接外推生产。

## 7. 执行顺序

1. 预检：`preflight.js`，确认公开读、登录、地址、SKU 池
2. 启动 Prometheus/Grafana/exporter，确认 target UP
3. 1 VU 基线 60s
4. 阶梯负载 20→60→100 VU
5. 100 VU 稳态期间记录 JVM/Tomcat/Hikari/DB 指标
6. 登录链路 10/s × 60s
7. 写链路 3 VU × 30s
8. 压测后采集 DB 统计、慢查询/EXPLAIN
9. 汇总报告

## 9. 风险与限制

- 同机压测：k6 与应用/数据库竞争 CPU、内存、磁盘，绝对数值偏低或抖动。
- 本地数据量小（SKU/SPU 约几十条），Seq Scan 可能仍然很快，索引问题会被掩盖。
- 100 VU 是并发连接数，不等于 100 个真实用户；真实用户还有多端、弱网、长连接等差异。
- 写链路只做冒烟，不能证明库存行锁和 Hikari 5 连接下的写容量。
- 监控采集本身有开销，Prometheus/Grafana 同机运行会进一步影响结果。
- 不修改代码/SQL，所有瓶颈只记录证据和建议，不在本轮修复。
