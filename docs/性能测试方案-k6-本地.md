# 尚品汇电商平台 k6 本地性能测试方案

> 版本：v1.1（评审后执行版）  
> 日期：2026-11-05  
> 被测环境：本地开发环境（非服务器、非生产）  
> 压测工具：k6 v2.3.0

## 1. 测试目标

验证本地尚品汇电商平台在只读浏览、登录、管理端查询场景下的吞吐与延迟表现，定位可能的性能瓶颈，为后续服务器容量测试和代码优化提供基线。

本轮只做**测量与定位**，不做代码优化。

## 2. 范围

### 2.1 纳入范围

| 层次 | 内容 |
|---|---|
| C 端公开读 | `GET /api/home`、`/api/products`、`/api/products/{spuId}`、`/api/search`、`/api/categories` |
| C 端鉴权读 | `GET /api/me`、`/api/cart`、`/api/orders`、`/api/favorites` |
| C 端登录 | `POST /api/auth/login`（手机号 + 固定验证码） |
| 管理端 | `POST /admin/auth/login`、`GET /admin/dashboard/stats` |
| 写链路冒烟 | 登录 → 加购 → 查购物车 → 下单 → 沙箱支付（仅 1 VU） |

### 2.2 不纳入范围

- 腾讯云服务器/生产环境压测；
- 高并发下单、支付、库存扣减；
- 代码优化、SQL 改写、缓存改造；
- Nginx/网关层容量（本地无 Nginx，直接打 8086）；
- 前端页面渲染性能（本轮只测接口）。

## 3. 环境与基线

| 组件 | 本地事实 |
|---|---|
| 后端 | `http://127.0.0.1:8086`，Spring Boot 4.1.1 |
| 商城前端 | `http://127.0.0.1:5174`（仅 UI 验证，不参与 k6 压测） |
| 管理端 | `http://127.0.0.1:5173`（仅 UI 验证） |
| PostgreSQL | `127.0.0.1:55434` |
| Redis | `127.0.0.1:56379` |
| k6 | v2.3.0，与后端同机运行 |
| 测试会员 | `13900000009`，验证码 `123456` |
| 管理端账号 | `admin / Admin@123` |
| 商品池 | 约 30 个 SPU，预检可售 SKU 20 个 |

> 注意：k6 与被测后端在同一台机器上，k6 自身 CPU/内存会与 JVM、PostgreSQL 竞争，结果不能直接等同于独立压测机数据；本轮用于**相对基线和瓶颈定位**。

## 4. 负载模型

参考电商浏览行为，`browse-load.js` 混合比例：

| 请求 | 比例 | 说明 |
|---|---:|---|
| 商品列表 `/products` | 40% | 首页/分类页瀑布流 |
| 搜索 `/search` | 25% | 含无结果冷门词 |
| 商品详情 `/products/{id}` | 20% | 含 SKU/库存聚合 |
| 首页 `/home` | 15% | 品牌 + 运营位 + feed，单请求最重 |
| 鉴权叠加 | 按 token 可用 | 类目、我的、购物车、订单、收藏 |

登录场景单独使用到达速率模式，避免混合负载掩盖登录瓶颈。

## 5. 测试场景

### 5.1 预检

```bash
k6 run observability/k6/preflight.js \
  -e BASE_URL=http://127.0.0.1:8086/api \
  -e ADMIN_BASE_URL=http://127.0.0.1:8086/admin \
  -e PHONE=13900000009 \
  -e ACCOUNT=admin \
  -e PASSWORD='Admin@123'
```

目的：确认接口、账号、token、地址、SKU 池是否满足压测前提。  
预检结果：公开读/登录/管理端全部 PASS；测试会员地址 0 条，写链路暂不可压测。

### 5.2 基线测试（Baseline）

```bash
k6 run observability/k6/browse-load.js \
  -e BASE_URL=http://127.0.0.1:8086/api \
  -e PHONE=13900000009 \
  -e VUS=1 -e DURATION=30s -e THINK_TIME=1 \
  --summary-export artifacts/k6/baseline-summary.json
```

目的：单用户下确认功能、延迟基线，排除数据/配置问题。

### 5.3 负载测试（Load）

```bash
k6 run observability/k6/browse-load.js \
  -e BASE_URL=http://127.0.0.1:8086/api \
  -e PHONE=13900000009 \
  -e STAGES=10s:5,30s:20,60s:40 \
  -e THINK_TIME=0.5 \
  --summary-export artifacts/k6/load-summary.json
```

目的：观察 5 → 20 → 40 VU 下的 RPS、P95/P99、错误率变化，判断线性扩展能力。

### 5.4 峰值/压力测试（Stress）

```bash
k6 run observability/k6/browse-load.js \
  -e BASE_URL=http://127.0.0.1:8086/api \
  -e PHONE=13900000009 \
  -e STAGES=10s:20,20s:50,20s:80 \
  -e THINK_TIME=0.2 \
  --summary-export artifacts/k6/stress-summary.json
```

目的：观察高并发下是否出现连接池耗尽、Tomcat 线程打满、P99 急剧上升或错误率升高。  
若本机资源明显不足，以“出现拐点”为准，不强行跑满。

### 5.5 登录风暴

```bash
k6 run observability/k6/login-load.js \
  -e LOGIN_TARGET=customer \
  -e BASE_URL=http://127.0.0.1:8086/api \
  -e PHONES=13900000009 \
  -e RATE=5 -e DURATION=20s \
  --summary-export artifacts/k6/login-summary.json
```

目的：固定 5 次/秒登录请求，观察 Redis 验证码校验、token 签发和 JWT/密码计算成本。

管理端登录可单独测 BCrypt CPU 成本：

```bash
k6 run observability/k6/login-load.js \
  -e LOGIN_TARGET=admin \
  -e ADMIN_BASE_URL=http://127.0.0.1:8086/admin \
  -e ACCOUNTS=admin -e PASSWORD='Admin@123' \
  -e RATE=2 -e DURATION=15s \
  --summary-export artifacts/k6/admin-login-summary.json
```

### 5.6 写链路冒烟（可选）

只有在测试会员补齐收货地址后执行，最多 1 VU、10 秒，目的是测接口延迟，不做写容量结论。

```bash
k6 run observability/k6/checkout-smoke.js \
  -e BASE_URL=http://127.0.0.1:8086/api \
  -e PHONES=13900000009 \
  -e VUS=1 -e DURATION=10s \
  --summary-export artifacts/k6/checkout-summary.json
```

## 6. 通过标准（初版）

| 指标 | 目标 |
|---|---|
| `http_req_failed` | < 1% |
| `checks` | > 99% |
| `http_req_duration` P95 | < 800ms |
| `http_req_duration` P99 | < 1500ms |
| 压测期间后端 | 无 OOM、无持续 5xx、无连接池耗尽 |
| 结果可复现 | 相同场景重复一次，P95 波动可解释 |

> 这些阈值是首版经验值。本轮结束后根据本地基线回填更合理的服务器阈值。

## 7. 观测指标

### 7.1 客户端

- `http_reqs`：总请求数、RPS；
- `http_req_duration`：avg/min/med/p90/p95/p99/max；
- `http_req_failed`：失败率；
- `checks`：业务断言通过率；
- `vus`、`iterations`：并发与迭代数。

### 7.2 服务端

- 后端日志：5xx、异常堆栈、慢请求；
- HikariCP：连接池等待/耗尽；
- Tomcat：线程占用；
- JVM：CPU、Heap、GC；
- PostgreSQL：连接数、慢查询、锁等待；
- Redis：延迟/命中率（如可观测）。

### 7.3 代码与 SQL 静态分析

结合以下路径分析潜在瓶颈：

- `backend/shang-commerce/.../CatalogReadService`：首页 feed、`toCard` 循环查询；
- `StorefrontController`：首页/列表/详情/搜索；
- MyBatis-Plus 查询：N+1、分页 COUNT、无索引条件；
- `HikariCP` 最大连接数；
- 登录链路：Redis、JWT、BCrypt。

## 8. 风险与控制

| 风险 | 控制 |
|---|---|
| k6 与后端同机，资源竞争 | 记录本机 CPU/内存；结论标注“同机基线” |
| 写链路污染本地数据 | 只跑 1 VU 10s；不跑批量下单 |
| 登录限流/验证码冷却 | 使用固定演示验证码；失败时记录而不是重试轰炸 |
| 压测把本地服务打挂 | 分阶段加压；出现 5xx/超时立即停止 |
| 本地方案不代表服务器 | 报告明确边界，服务器测试另立任务 |

## 10. 方案评审记录

### 10.1 评审发现

| 问题 | 优化 |
|---|---|
| 原方案只有全局 `http_req_duration`，无法定位首页/列表/详情/搜索哪个接口慢 | 在 `browse-load.js` 增加按接口的 `Trend`：`endpoint_home_duration`、`endpoint_products_duration` 等 |
| 原方案写“写链路可选”，但没有明确本地地址前置条件 | 预检确认测试会员没有地址；本次仅为写冒烟补一条本地测试地址，仍限制 1 VU / 10s，不做写容量结论 |
| 原方案没有明确“同机压测”的偏差 | 在报告中标注 k6 与 JVM/PostgreSQL 同机竞争，结果只作相对基线 |
| 原方案只有客户端指标，缺少代码/SQL 证据 | 增加 `pg_stat_user_tables`、`EXPLAIN`、代码路径分析 |
| 压力测试可能导致本地服务不稳定 | 分阶段 20→50→80 VU；出现持续 5xx 立即停止 |

### 10.2 评审结论

方案 v1.1 通过，执行范围确定为：

1. 预检；
2. 基线 1 VU / 30s；
3. 负载 5→20→40 VU / 100s；
4. 压力 20→50→80 VU / 50s；
5. C 端登录 5/s / 20s；
6. 管理端登录 2/s / 15s；
7. 写链路 1 VU / 10s（仅接口冒烟）。

不执行：高并发写、库存压测、服务器/生产压测、代码优化。
